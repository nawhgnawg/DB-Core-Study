# 📌 [Chapter 2] 동시성 제어: 비관적 락(Pessimistic) vs 낙관적 락(Optimistic)

## 💡 핵심 요약 (Key Concept)

### 1. 동시성 문제: Lost Update (로스트 업데이트)
* 두 개 이상의 트랜잭션이 동시에 같은 데이터를 읽어 수정할 때, 나중에 커밋된 트랜잭션이 먼저 커밋된 변경사항을 덮어써 버리는 현상.

### 2. 비관적 락 (Pessimistic Lock)
* **메커니즘:** DB 레벨에서 `SELECT ... FOR UPDATE` 구문을 통해 조회 시점부터 쓰기 잠금(X-Lock)을 획득.
* **특징:** 충돌을 원천 차단하여 정합성이 완벽하지만, 타 스레드가 대기(Blocking)하므로 성능 저하 발생.

### 3. 낙관적 락 (Optimistic Lock)
* **메커니즘:** DB 락을 걸지 않고, Entity의 `@Version` 필드를 통해 저장 시점에 버전 변경 여부(`UPDATE ... WHERE id=? AND version=?`)를 검증.
* **특징:** DB 락이 없어 성능이 뛰어나지만, 충돌 발생 시 애플리케이션 레벨에서 예외(`OptimisticLockException`) 처리 및 재시도(Retry) 로직을 직접 구현해야 함.

---

## ⚖️ 비관적 락 vs 낙관적 락 Trade-off 비교

| 구분 | 비관적 락 (Pessimistic) | 낙관적 락 (Optimistic) |
| :--- | :--- | :--- |
| **제어 주체** | Database (DB Lock) | Application (`@Version`) |
| **성능 (Throughput)** | 낮음 (대기 시간 발생) | 높음 (락 없이 즉시 처리) |
| **데이터 무결성** | 100% 보장 | 충돌 시 예외 및 재시도 필요 |
| **적합한 환경** | 충돌 빈도가 높거나, 결제/재고 등 정합성이 핵심인 경우 | 충돌 빈도가 낮고, 조회 중심인 경우 |
| **주요 리스크** | 데드락(Deadlock) 가능성 | 핫스팟(Hot Spot) 시 재시도 폭증으로 CPU 낭비 |

## 💫 면접 대비 Q&A

**Q. 트래픽이 매우 몰리는 선착순 쿠폰 발급 시스템에는 어떤 락이 적합한가요?**
> **A.** 충돌 빈도가 극도로 높은 '핫스팟' 환경에서는 낙관적 락 사용 시 수많은 재시도(Retry)로 인해 CPU 낭비가 심해집니다. 따라서 DB 레벨에서 순차적으로 줄을 세우는 **비관적 락**이나, **Redis 기반의 분산 락(Distributed Lock)**을 사용하는 것이 적합합니다.

**Q. 낙관적 락에서 충돌 발생 시 애플리케이션은 어떻게 대응해야 하나요?**
> **A.** 충돌 시 던져지는 예외를 캐치하여 1) 사용자에게 "다시 시도해 주세요"라는 안내 메시지를 전달하거나, 2) Facade 레이어에서 `while`문과 무작위 지연(Backoff)을 활용한 자동 **재시도(Retry) 로직**을 수행합니다.
