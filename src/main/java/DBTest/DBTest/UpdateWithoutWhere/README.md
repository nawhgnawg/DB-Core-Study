# 📌 [Chapter 3] WHERE 절 누락과 Table Lock (장애 방어)

## 💡 핵심 요약 (Key Concept)

### 1. DB Index와 Lock의 관계 (InnoDB)
* MySQL InnoDB의 Record Lock은 **인덱스 레코드(Index Record)**를 기준으로 잠금을 겁니다.
* WHERE 절에 적절한 인덱스 조건이 있다면 해당 행(Row)만 잠그는 **Row Lock**이 동작합니다.
* WHERE 절이 없거나 인덱스를 타지 못하면 **Full Table Scan**이 발생하며, DB 엔진은 읽어 들이는 모든 레코드에 락을 걸어 사실상 **Table Lock**으로 동작합니다.

### 2. 장애 발생 메커니즘 (Cascading Failure)
1. `UPDATE user SET cash = 0` (WHERE 절 누락) 실행
2. 전체 Record에 배타적 락(X-Lock) 획득 (롱 트랜잭션 진행)
3. 일반 유저들의 모든 DB 쓰기 요청이 Block 대기 큐에 누적
4. `LOCK_TIMEOUT` 초과로 타임아웃 예외 발생 및 커넥션 풀(HikariCP) 고갈 ➔ **전체 서비스 마비**

### 3. JPA 지연 쓰기(Write-Behind)의 착시 현상
* `user.setCash(0)` 호출 시 자바 코드는 즉시 에러를 내지 않고 1차 캐시만 변경하므로 "성능/성공" 로그가 먼저 찍힘.
* 실제 트랜잭션이 커밋되어 **Flush**되는 시점에 DB로 `UPDATE` 쿼리가 전송되며, 이때 DB 락 대기에 걸려 타임아웃 에러가 터짐.

## 🛡️ 실무 예방 및 방어 전략

1. **Chunking / Batching (청크 분할):** 대량 업데이트는 100만 건을 한 번에 실행하지 않고, PK 기반(`WHERE id > ? LIMIT 1000`)으로 1,000건씩 자르고 트랜잭션을 짧게 끊어서 처리.
2. **Short Transaction:** 트랜잭션 내에 외부 API 호출이나 불필요한 연산을 제거하여 락 점유 시간을 최소화.
3. **실행 계획 검증 (EXPLAIN):** 운영 DB 쿼리 실행 전 반드시 `EXPLAIN`을 통해 Full Table Scan 여부 확인.

## ⚖️ 대량 업데이트 처리 전략 비교

| 구분 | 단일 쿼리 대량 업데이트 (`No WHERE`) | 청크 분할 업데이트 (`Chunked`) |
| :--- | :--- | :--- |
| **락 범위** | 전체 레코드 (`Table Lock`) | 1,000건 범위 레코드 (`Row Lock`) |
| **타 요청 영향** | 다른 유저의 쓰기 요청 전면 차단 | 청크 사이의 틈(Gap)에 타 요청 정상 처리 |
| **트랜잭션 길이** | Long Transaction (위험) | Short Transaction (안전) |
| **장애 리스크** | 커넥션 풀 고갈 및 전체 마비 | 없음 (동시성 확보) |

## 💫 면접 대비 Q&A

**Q. UPDATE 쿼리에 WHERE 절을 넣었는데도 Table Lock이 걸리는 경우가 있나요?**
> **A.** 네, 1) WHERE 절의 컬럼에 인덱스가 없어 Full Scan이 발생하는 경우, 2) 인덱스가 있더라도 변경 데이터가 전체의 20~30% 이상을 차지하여 DB 옵티마이저가 인덱스 타는 것보다 Full Scan이 이득이라고 판단하는 경우, 3) 인덱스 컬럼에 형변환이나 함수를 적용해 인덱스가 파괴된 경우에 전체 락이 걸릴 수 있습니다.

**Q. 대량의 데이터를 업데이트할 때 서비스 장애를 방지하기 위한 핵심 로직은?**
> **A.** PK(ID) 기반으로 **1,000건 단위 청크(Chunk)로 잘라 트랜잭션을 짧게 끊어주는 것**입니다. 각 청크 완료 후 아주 짧은 대기(Sleep) 시간을 주어 다른 유저들의 단건 트랜잭션이 락을 획득할 수 있는 틈새를 제공해야 합니다.
